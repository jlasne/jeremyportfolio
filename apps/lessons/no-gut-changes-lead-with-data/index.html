Make no gut changes, lead with data

I broke my own data on Kaught. I shipped too many changes in one update, and the numbers moved. A few metrics went up, others went down, and I could not tell which change caused which move, so the update taught me nothing.

Here is how I change my apps now.

Start simple, then get volume.

Ship a simple first version. Then bring users in, because a test on 200 people tells you nothing you can trust. I wait for at least 1,000 users in a test, and more when the traffic allows it, before I decide anything at all.

Give it time and volume.

One change at a time.

Change 2 things, and you learn nothing. If the number goes up, you can’t say which change did it. If one change helped and the other hurt, they cancel out, and you throw away a good idea without ever knowing it was there.

So each test changes one thing: one headline, one price, one screen.

3 zones, one test each.

I run 3 tests at most. One on the onboarding, one on the pricing, and one inside the app. For pricing, that means one test across all paywalls at once, because 2 paywall tests at the same time mix their users and blur both answers.

I measure each one in PostHog.

Everything else is an update.

Fixes skip the queue. A bug is a bug: fix it the same day, with no test. New content skips the test too, because it is a marketing moment: announce what is new to your email list, in a notification and on your socials.

Every update is a launch.

Read the result right.

A winner on day 3 can be a loser by month 3. 55% of 3-day trial cancellations happen on day 0, and refunds arrive weeks later. So I keep each test running until real payments come in, then check the winning group again at 3 and 6 months.

Only then do I let the data decide which version stays in the app.

Make no gut changes. Lead with data.
